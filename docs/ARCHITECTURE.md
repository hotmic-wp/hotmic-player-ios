# HotMicPlayer architecture (0.3.0)

The dependency-free player package defines `HMPlayer`, its VOD engine, `HMVerticalFeedView`, analytics and three partner adapter protocols. The separate [HotMicPlayerConnect package](https://github.com/hotmic-wp/hotmic-player-connect-ios) will depend on this package and HotMicCore to implement those adapters. There is no Core code here.

## Public contract and atomic playlist edits

`@MainActor @Observable HMPlayer` is the only playback owner. Public value types describe entries, sources, snapshots and events. Native `HMPlayerPool`, `HMPlayerNode`, the cache proxy and video-surface views are internal. Analytics sinks can still attach to native layers through the existing hub contract.

`HMPlaylistState` computes edits and validates the full resulting list before committing. The current item is tracked by stable ID and mapped to its new index when earlier entries disappear. Upcoming/insert/append/removal of other entries preserve the assigned active node, `AVPlayerItem`, layer, activation and media clock. `replaceAll` explicitly ends the old activation and resets resume positions. Removing current selects the next surviving entry after its old index, then the previous survivor; no survivors means idle.

Every effective edit increments a playlist revision; no-op edits do nothing. The scroll bridge and quiet-period fallback commit by item ID. The bridge cancels animation/deceleration only if the current or destination ID changes position. Appends and edits to an unrelated tail preserve the in-progress swipe. Removing current anchors to its survivor. This defines the result even when several edits arrive in one run-loop turn during a drag.

Partner edits preserve pending page fetches and the cursor. Source pages drop overlapping/repeated IDs with a non-fatal event, advance their cursor and append through the usual refresh path. Only changing the source or teardown invalidates the generation. Late pages from an old source cannot append. Low-water paging uses the configurable number of entries after current.

## Hybrid two-player engine and prefetch

Default S3 has one active native player and one prepared next player, plus an independent bounded data window. S0 has one direct player, S1 adds data prefetch, and S2 preserves the warm-pool comparison. The default adaptive policy reduces speculative work within app budgets using measured throughput, latency, readiness, dwell and buffer health; see [Adaptive prefetch](ADAPTIVE_PREFETCH.md).

The resolution window is current plus configured data/warm offsets. `HMResolutionStore` coalesces pending tasks for an immutable entry, caches completed metadata for the player session, and cancels unfinished resolution when the entry leaves the window. Current and next resolution use user-initiated priority; other neighbours use utility priority. A higher-priority waiter promotes existing work as roles change. Errors retry with capped backoff and a three-attempt budget, reset on current activation. Direct extensionless `.auto` URLs use a HEAD response to distinguish HLS from MP4, falling back to a streamed GET of bytes 0–1 if HEAD fails. Explicit formats and known extensions avoid that request.

Media prefetch is gated on current buffer safety, with hysteresis around the threshold. Resolution runs independently of that gate. An identity change in the window cancels obsolete speculative work immediately, releases removed routes/requests and trims the displaced next player. A safe current buffer allows the new next assignment to prepare immediately. Otherwise it waits for safety so speculative work cannot queue ahead of the current item. Prefetch identity changes with the configuration, order and resolved URLs; unchanged-window edits and no-op buffer ticks do not restart tasks or reset buffer hysteresis. Pool assignments and route retention compare complete items, including source, rather than only IDs.

## Loopback transport and cache ownership

One `NWListener` serves loopback HTTP routes for MP4 and HLS. The transport actor owns requests, streams and payloads; a locked small snapshot exposes only healthy port, route and cache-size state to the main actor. The listener port is published only after a HEAD health request proves host ATS access. Failed startup leaves direct playback available. Next use and foreground re-arm a dead listener, repeating ATS/health verification before publishing a port. A playback-time loopback failure has a direct fallback retaining the activation clock.

Current origin requests use high priority. Speculative requests use low priority and a separate URLSession connection pool. Connection caps are eight per host. Fetcher state (`pending`, `task`, `response`, counters and completion) is lock protected. Streamed responses suspend upstream work while the player applies backpressure. URLSession's request deadline is extended for those streams; an explicit 20-second inactivity watchdog runs only when upstream work is permitted. A deliberately paused, full-buffer player therefore does not time out. Cancellation and watchdog expiry settle the continuation once.

A streamed origin response emits one transfer event with its total received bytes, including partially received failed responses, rather than one event per chunk. Bounded range fetches emit one event per upstream response. Cache reads emit their delivered cache bytes. Media bytes are stored in bounded 512 KiB ranges, and the disk LRU cap is hard even when the window exceeds it. Cache identity preserves query parameters unless an app explicitly declares particular signing parameter names volatile.

The window retains current routes while upcoming routes are pruned. Removed playlist media owners are released. Equal root URLs and known shared HLS child resources are preserved for remaining owners. Resources are pinned only as a preference within the hard cap. HLS playlists never persist to disk: they are cached in memory with configurable TTL (default 30 seconds). Route/waste retention scans run on window changes and task completion, not after each streamed chunk. Wasted bytes compare speculative range unions with ranges delivered to activated playback; warm-only delivery is not counted as watched.

## Overlay-by-clock model and interaction lifecycle

An overlay is a pure rendering function of `(media clock, timeline)`. Chat queries a time window; reactions replay at their authored offsets; density and clustered markers are precomputed. Seeking changes the media clock and therefore rewinds all overlay layers consistently. A tick changes progress and the density mask, without rebuilding the density path or scanning every event.

`HMInteractionSource.timeline(for:)` supplies this clock-indexed data without opening a session. Synchronous lifecycle hooks own current and next only. `willBecomeNext` prepares next, `didBecomeCurrent` promotes current, and `didLeave` closes entries outside both roles. Promotion keeps an already-open next session. Hiding or tearing down closes both. Optional actions belong to the host adapter; default implementations throw unsupported, and `capabilities(for:)` (default read-only) tells the UI which exist. `HMMockInteractionSource` wraps deterministic `HMMockTimeline` for the demo.

### Engagement layers

`HMEngagement` sits between the timeline and any UI. It is created once per playlist entry by `HMPlayer.engagement(for:)`, folds the timeline once (reaction totals, authored moments) and then maintains those aggregates incrementally. Queries are windowed by media time and backed by the timeline's binary search, so a body that calls one on each playback tick starts with an O(log n + k) timeline lookup, then merges and filters local state. Each query reads an observable `revision`, which every mutation bumps; that is how SwiftUI invalidates on a vote, a sent message or a source push without the timeline itself being observable.

Viewer actions are optimistic and keep their local state beside the timeline: pending messages (merged into chat queries until the source accepts them), the viewer's confirmed chat and stream reactions (an offset-sorted list merged into chat and reaction queries, also appended to the timeline), message-reaction deltas and votes. The confirmed list exists because `HMStreamTimeline.append` may legitimately do nothing; merging de-duplicates by ID, so an appendable timeline or a source echo never shows an event twice. When the source returns the confirmed server event from `sendChat`/`react`, the local event is replaced under the server ID (the viewer's offset and reaction weight are kept), and a server-to-local ID map keeps list-row identity stable. IDs folded in from `receive(_:)` are remembered, so an echo that arrives before its confirmation is not counted twice. A source failure removes the local state and rethrows. Capabilities are checked before anything changes.

Source moderation updates are main-actor methods on the same observable engagement. `removeMessage(id:)` accepts a server ID or a local row ID, drops pending and confirmed-own payloads, clears message-reaction overlays and remembers deleted IDs. `removeReaction(_:forMessage:count:isOwn:)` subtracts message-reaction counts with a zero floor and can clear the viewer's selection. These reactions have no per-reaction identity, so the adapter must deliver each count deletion once (or replace authoritative totals with `updateReactions`). `removeReaction(id:)` deletes a stream event and reverses the exact magnitude originally folded into reaction totals. Message and stream deletions are idempotent; removal records ignore later echoes and send confirmations. Sources with message-reaction totals should prefer `updateReactions(_:forMessage:)`; count removal is for deletion deltas, which lack individual reaction IDs.

`HMPlayer` owns a payload-free `HMModerationState` per playlist item ID, shared by that item's engagement instances. Message/stream-event and poll deletion IDs survive ordinary engagement/timeline eviction, apply before folding history or importing source polls on rebuild, and stay observable to a new engagement even if a source still holds an older instance. They do not count as viewer state or pin the full engagement. Records are removed when the item leaves the playlist (including replacement) or the player tears down. Standalone engagements own the same bounded store for their own lifetime.

Each item stores at most 4,096 deletion IDs and 256 KiB of combined UTF-8 ID payload, plus bounded Set overhead. To prevent resurrection at the bound, exceeding either limit replaces the records with a flag that hides all of that item's engagement, including future events/polls and waveform, until the item lifetime ends. It never drops the oldest deletion to make room for a newer one. There is no reinstate API.

The underlying `HMStreamTimeline` contract remains unchanged: it can be immutable, and its raw events/aggregates can still contain deleted data. UI components read the engagement's filtered queries. Event additions/deletions invalidate the waveform projection; the next `density` or `markers` read rebuilds it once, and both getters reuse that cache. Poll changes, message-reaction counts, pending chat and action-result changes do not dirty the waveform. If the source's available events already exclude the deletion (or a removed pending event was never appended), the SDK keeps the source's own density/peaks and weighting. Otherwise it derives both from surviving available events using **SDK aggregation**, preserving the source's bucket count (60 when absent). Arbitrary normalized source weights cannot be inverted from buckets; sources must expose contributing events for this fallback, or update their own timeline's events and aggregates together to retain their weighting. The SDK cannot infer source-only weights from an event ID.

Local confirmed/incoming events are sorted only when their cache is dirty. Incoming payloads are retained locally only if the timeline ignores append. Queries linearly merge ordered source/local windows, de-duplicate IDs and filter removal records; pending chat is inserted in order and merged the same way. There is no unconditional sort on the 10 Hz query path. An unsorted partner window is normalized only when needed; returning events in media-time order avoids that fallback.

`upsertPoll(_:)` replaces the complete poll by ID and reorders it by opening time; `update(_:)` forwards to it and is deprecated with `renamed: "upsertPoll(_:)"`. A known source viewer vote replaces local state; an omitted vote preserves an in-flight choice only while its option exists. `removePoll(id:)` records even a not-yet-seen poll ID, clears the card/local vote state, and ignores every later upsert with that ID, including after eviction and rebuild. A poll must use a new ID to represent a new poll. Vote operation tokens and source-update versions keep late success/failure from changing removed polls or overwriting authoritative updates. Message-reaction rollback similarly yields to authoritative source updates. Chat row IDs stay stable across confirmation. With normal motion, outgoing rows use an identity transition so moderated text does not linger in a fade; Reduce Motion keeps the existing cross-fade.

Ownership: the player holds the source; player-created engagements reference it weakly; sources reference engagements weakly. A standalone engagement retains its source. The player's engagement and timeline caches follow the prefetch window plus the previous entry (a kept engagement keeps its timeline), keeps any engagement holding viewer state while its entry is in the playlist, looks entries up through an ID index rebuilt after each playlist edit (overlay bodies call it every tick), and serves inert engagements for items outside the playlist. Without a source the player uses an internal empty source, so no content is ever invented.

`HotMicPlayerUI` is a separate target that depends only on `HotMicPlayer`. Components are plain views over `HMEngagement` plus a media time; none reaches into the player. Layouts (`HMEngagementLayout`) are the only place that touches `HMPlayer` (seek, play/pause, mute, interaction deferral). The scrubber keeps the 0.2 performance property: its bars are a `Shape` over the density array, revealed by masks whose width is the only per-tick change. Floating reactions sample the timeline slice crossed since the last tick and emit only where the waveform under the playhead clears a floor, so what flies always matches what the scrubber shows.

## Events, Observation and measurement

Each `HMPlayer.events` access creates an independent ordered AsyncStream with a 256-event newest buffer. Streams finish at teardown or finishRun; task cancellation removes their continuations. Observation exposes list/current/paging state, last event and snapshots. Player notifications translate native readiness/first-frame/stall/error telemetry; analytics continues to fan out through the existing hub/sink contract.

Readiness (`cold`, `cachedBytes`, `warmPlayer`) is recorded at activation. TTFF runs from the request clock to a visible display-link boundary after the layer was ready and crossed a display boundary. It estimates presentation to about one refresh period. `firstFrame` carries seconds in the public event stream and milliseconds in analytics. Benchmark startup summaries, transfer accounting, runEnd, JSONL, mock sources and experimental configuration are available only through Benchmark SPI. Partner presets and the stable budget knobs form the configuration contract.

## Supported scope and remaining coverage

Immutable VOD, MP4 and HLS, iOS 17+ and zero package dependencies are the partner contract. Snapshot live/DVR fields remain for telemetry compatibility but do not broaden that contract. Live, LL-HLS, DRM, authenticated origins, signed-playlist refresh, HLS byte-range/alternate-audio coverage and concurrent active controllers sharing a disk directory are outside supported coverage. Physical-device decoder, memory, thermal and audible continuity still require device validation. Poster URLs are supported; generating a poster from the first frame is deferred.

Paging retries are separate from reference-resolution retries: four total page attempts, with 1/2/4-second exponential waits. The scheduler checks the budget before scheduling another request, including rejected pages. A successful `replaceAll` advances the cursor generation and resets the cursor; it discards old-generation page results without cancelling the transport request. Other playlist edits retain the current source request. Audio-session ownership is a public configuration choice; with `managesAudioSession == false`, all activation and teardown paths leave the host session alone.

### 1.0 moderation synchronization

The record store holds weak references to living engagements, pruning dead references on registration and notification. Deletion and authoritative reaction-count writes notify those engagements synchronously on the main actor. Projection into observable arrays/totals happens on that mutation path, never in query getters. Waveform and sorted-local-event caches remain Observation-ignored and may rebuild lazily. No task or strong ownership cycle is introduced.

Authoritative message counts live in the bounded record store and override a timeline's stale counts, including after engagement eviction/rebuild. Local optimistic reactions and deletion deltas overlay those counts; authoritative updates clear local deltas and advance rollback versions. Count-removal deltas alone are instance-local. Overflow emits one `Logger.error` under `com.hotmic.player` / `moderation`, with item ID and bounds, then suppresses future engagement for that playlist-item lifetime.
